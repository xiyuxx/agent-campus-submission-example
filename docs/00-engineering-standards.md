# 工程与验证约定

本文是前置准备阶段制定的实施基线。已选择素材审核与发布排期题，见 `06-topic-selection.md`。题目具体要求优先；具体技术选型与业务语义以 [架构基线](10-architecture-baseline.md) 为准，下文保留通用规范与早期选型原则。

## 1. 完成标准

交付围绕一条完整业务链路：输入 → 模型选择动作 → 工具执行 → 工具观察回传模型 → 模型调整动作或结束 → 结果与证据。

必须满足：

- 选择一道题，提取全部验收点并建立“需求—实现—测试—证据”映射。
- 至少一个由真实模型驱动的工具循环。模型看到工具结果后能够决定下一步。
- 至少两条真实模型路径体现不同工具结果导致的动作调整；仅结束条件不同也应说明业务意义。
- 至少三组实际运行材料覆盖正常、资料或信息不足、工具失败，整体覆盖所选题全部验收点。
- 执行上限、异常和不完整状态可观察且可测试。
- 可复制的安装、运行和验证步骤；完整五份文档、依赖和配置示例。
- GitHub URL、题号、最终 commit SHA 完整；私有仓库评审权限需核实。

真实模型不可用时仍完成离线流程，但必须把真实模型决策和相关证据标记为未验证，不能宣布全部达标。

## 2. 选题方式

看到四道题后，各项按 1–5 分评分；加权分为 `Σ(评分 / 5 × 权重)`。评分只辅助判断，必须附具体原因。

| 维度 | 权重 | 判断依据 |
| --- | --- | --- |
| 业务目标清楚 | 25 | 用户、输入、输出及成功条件能否准确界定 |
| 模型动态决策必要性 | 25 | 是否自然存在观察后补查、换工具、澄清或停止等动作 |
| 资料与工具可获得性 | 20 | 合成数据或本地工具能否在时间内真实支撑核心业务 |
| 验收可验证性 | 20 | 能否建立客观断言和三类场景，覆盖全部验收点 |
| 实现成本可控 | 10 | 三小时内能否完成可运行链路并留出验证和文档时间 |

优先排除缺少关键输入且无法合法替代、主要依赖难以接入的外部系统、或无法在时间内证明核心效果的选项。
最终说明选择原因、其他选项的主要成本、剩余风险和最小交付范围。已完成的选择记录见 [选题比较](06-topic-selection.md)。

## 3. 项目结构与职责

以下为选题后的建议结构，按业务删减；不提前创建空抽象或无用模块。

```text
README.md
AGENTS.md
pyproject.toml              # Python 确定后创建：包定义、工具配置、直接依赖
requirements.lock          # 选定安装方案后生成与验证的精确依赖
.env.example
src/shadow_agent/
  __init__.py
  __main__.py               # CLI：参数、输入输出、退出码
  config.py                 # 配置、校验与默认限制
  contracts.py              # 动作、工具观察、结果、Trace 数据契约
  agent.py                  # 模型—工具循环与执行预算
  models/                   # 真实模型适配器、离线模型替身
  tools/                    # 工具白名单、参数校验、业务实现
tests/{unit,integration,live}/
examples/                  # 实际输入、输出、Trace、测试结果
data/                      # 合成资料与规则
docs/00-engineering-standards.md
docs/01-requirements.md
docs/02-solution.md
docs/03-evaluation.md
docs/04-ai-usage.md
docs/05-retrospective.md
```

CLI 不实现业务判断；Agent 不嵌入具体供应商传输逻辑；模型不能绕过工具白名单执行任意代码。
工具应返回结构化结果，业务失败使用明确错误类型。共享状态尽量小，避免全局可变对象。

## 4. 技术栈选择规则

暂定 Python + CLI + 单 Agent：便于集中实现决策循环、构造合成资料与自动测试，减少界面和部署工作。
当前检测到 Python 3.13.12；它只是环境事实，需按模型 SDK 兼容性确定最终解释器并验证。

| 项目 | 暂定原则 | 升级条件 |
| --- | --- | --- |
| 运行入口 | CLI，JSON 输入和输出，日志走 stderr | 题目验收或业务交互明确需要 HTTP API / Notebook |
| Agent Runtime | 原生有界循环 | 框架显著降低状态管理、工具接入或恢复成本 |
| 模型 | 可访问且支持工具调用或结构化动作的真实模型 | 按可用性、中文业务能力、延迟、成本实测决定 |
| 数据与存储 | 小型 JSON / JSONL / 文本；必要时 SQLite | 题目确需持久化、检索规模或并发 |
| 数据契约 | 标准库类型、显式校验；复杂时引入 Pydantic | 嵌套协议校验收益超过依赖成本 |
| 测试与质量 | pytest；Ruff 格式化和静态检查 | 配置后实际执行，精确版本入锁文件 |
| 配置 | 环境变量 + 命令行，显式区分 live / mock | 仅业务确需时增加配置层 |

每引入一个依赖，记录其职责、版本、使用功能、替代方案和实际收益。
如使用 LangGraph、ADK 或 AgentScope 等，说明框架承担的职责，不重复实现同一 Runtime。
不提前绑定供应商，不把 SDK 示例改名当作业务实现。

环境隔离使用 `venv`，包采用 `src` 布局。依据：[Python venv 文档](https://docs.python.org/3/library/venv.html)、[pytest 项目组织建议](https://docs.pytest.org/en/stable/explanation/goodpractices.html)。

依赖锁定后验证干净环境安装；使用 Python 包时通过安装项目导入，不在代码中修改 `sys.path`。

## 5. 代码规范

- Python 文件 UTF-8，四空格缩进，行长暂定 100；选型确定后写入工具配置。
- 模块与函数 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE_CASE`。
- 对公开函数、模型和工具边界使用类型注解；时间、预算和返回类型应明确。
- 一个函数承担可描述的单一职责，抽象只服务当前用例。
- 注释解释业务规则、失败原因和取舍，避免逐行翻译代码。
- 捕获预期异常并保留错误上下文；不得 `except: pass` 或把异常伪装成成功。
- 配置缺失快速失败；秘密不得进入输出、日志和测试快照。
- 工具参数不直接拼入 shell；涉及写入的业务工具明确校验范围和副作用。
- 用户资料和检索内容作为数据处理，不得覆盖系统约束或获得额外工具权限。
- 跨平台路径用 `pathlib`；测试不依赖本机绝对路径和网络。
- 标识符使用英文，交付说明和必要业务解释使用中文。

## 6. Agent 决策与边界

动作契约至少包含：动作类型、工具名、参数、简短决策依据；或最终状态、结论与依据。
工具观察至少包含：成功与否、数据摘要、错误码、是否可重试、相关资料 ID。

每轮将工具观察加入模型上下文，再请求下一动作。正常的语法校验、工具分发和预算控制可由程序完成，业务动作由模型选择。

模型行为与程序策略要分开说明：超时重试是程序策略；看到资料缺失后选择补查或询问用户才是业务决策。
离线模型替身可根据观察返回不同动作以测试协议，但该行为是脚本逻辑，不计作真实模型决策证据。

限额定稿为每素材 16 次模型请求尝试、16 次工具尝试、总时长 180 秒；每请求最多 3 项、总时长 540 秒。临时传输错误额外重试最多 1 次。传输超时与整次请求截止时间分别控制，详见架构基线。
模型请求的重试消耗请求预算；工具重试消耗工具预算。并行工具若启用则逐个计数。
还应设置总运行截止时间，所有重试受到剩余时间约束。任何无效动作和纠错都不能无限循环。

终态应按业务细化，至少区分：

| 状态 | 含义 |
| --- | --- |
| `completed` | 核心目标完成且必要依据齐备 |
| `needs_input` | 需要用户补充信息，列出具体缺口 |
| `incomplete` | 步数、调用或时间上限耗尽，返回已有结果和未完成项 |
| `failed` | 无法继续的工具、配置或模型错误 |

预算耗尽不得自动改写为成功。允许模型输出 `completed` 前，程序核对结构化必填项和可验证的完成条件。

## 7. Trace 与证据

Trace 必须由实际执行过程自动产生，不能事后手写成“真实日志”。建议 JSONL 事件包含：

| 字段 | 含义 |
| --- | --- |
| `run_id`, `event_id`, `step`, `timestamp` | 执行、事件、步骤和带时区时间 |
| `mode`, `model` | live / mock 与实际模型标识 |
| `event_type` | model_action / tool_result / final / error |
| `tool`, `arguments` | 工具名及脱敏参数 |
| `observation` | 结果摘要、业务错误和资料 ID |
| `reason_summary` | 模型对所选动作的简短说明，不要求内部思维过程 |
| `next_action` 或后续事件关联 | 从观察到后续动作的可追踪关系 |
| `status`, `elapsed_ms`, `budget_remaining` | 状态、耗时与剩余预算 |

每个用例保存输入、实际输出、Trace 和运行元数据。实际值不能混入“预期输出”。
两条动态路径应展示共同决策点、不同观察以及模型实际选择的不同后续动作，例如：资料齐全后完成，资料缺失后补查。
这只是设计示例，不能写入评估结果当成真实执行。

## 8. 测试与效果评估

先从验收点写清预期，再运行并保存实际结果。默认测试离线、无密钥、无付费、可重复。

| 类别 | 核心断言 |
| --- | --- |
| 正常输入 | 业务产出满足验收约束；引用和状态可核查 |
| 信息或资料不足 | 不编造缺失事实；补查、澄清或明确未完成符合业务要求 |
| 工具失败 | 错误可观察；按业务选择替代、重试或停止；调用受限 |
| 模型协议异常 | 未知工具、非法参数、无效结构不触发任意执行，不无限纠错 |
| 预算与超时 | 所有调用与重试计数正确；耗尽后终态明确未完成 |
| 配置边界 | Mock 无密钥可用；live 缺配置报明确错误 |
| 真实模型评估 | 工具观察被传回模型；至少两条不同动作路径有实际 Trace |

优先使用事实型断言：字段、规则、引用有效性、调用上限和任务是否完成；避免断言模型措辞逐字相同。
涉及检索时检查引用资料是否存在、结论是否受资料支持，涉及计算时用独立确定性期望值核验。
模型质量评估单列人工判定准则和失败样例；报告样本量、配置和运行次数，小样本结果不外推。

真实模型测试显式启用，记录费用或调用量（仅在可获得时）。受控工具故障可用于 live 评估，但需注明注入方法。
不将离线单测通过率作为真实模型任务成功率。覆盖率仅作辅助，不预设无依据的百分比目标。

## 9. 三小时实施预算

这是计划，不是实际用时。准备阶段单独记账；实际阶段时间在发生后填写。

| 阶段 | 计划分钟 | 产出 |
| --- | --- | --- |
| 选题与需求拆解 | 15 | 选择理由、验收矩阵、最小范围 |
| 最小完整链路 | 65 | CLI、真实模型、工具循环、执行限制 |
| 异常与离线入口 | 25 | Mock、缺信息、工具失败处理 |
| 测试与真实运行 | 40 | 三组证据、至少两条动态路径、测试结果 |
| 文档与交付核查 | 25 | 五份文档、干净安装、提交信息 |
| 缓冲 | 10 | 修复阻塞问题 |

优先削减界面、部署、复杂记忆和框架扩展。不得削减核心模型决策循环、三类证据和真实说明。

## 10. 最终检查

- [ ] 全部题目验收点有实现、测试和真实证据映射。
- [ ] 真实模型循环可运行，至少两条路径展示观察后的决策变化。
- [ ] 三类输入、实际输出、Trace、运行元数据完整。
- [ ] 步数、调用、时间、异常及未完成状态经验证。
- [ ] Mock 入口可离线运行，能力边界准确标注。
- [ ] 依赖已锁定，干净安装与 README 命令经过执行。
- [ ] 质量检查和测试结果已保存到 examples/ 并被评估文档引用。
- [ ] 五份文档与最终代码一致，AI 使用与本人贡献如实填写。
- [ ] 无密钥、个人信息、完整试卷和误提交的环境文件。
- [ ] 实际用时、已知限制和未完成项明确。
- [ ] 题号、GitHub URL、最终 SHA、评审访问权限已核实。
