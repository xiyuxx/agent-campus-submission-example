# Git 提交与阶段管理规范

用户要求：每完成一个阶段性任务就执行一次本地 Git 提交。完成必须有可核查产出和与修改相称的验证；不得把未验证功能写成已完成。

## 提交时机与阶段

每个可独立说明、验证和回退的任务形成一次提交，大阶段中可拆多个完整任务。不要积累到项目结束才提交，也不要为凑次数提交空内容。

| 阶段 | 典型产出 | 提交前验证 |
| --- | --- | --- |
| 设计与仓库规范 | 需求、架构、数据契约、Git 规范 | 文档链接、JSON 示例、密钥排除、钩子检查 |
| 数据契约与存储 | 类型、合成数据、SQLite、规则基础 | 格式、时间、事务与唯一约束测试 |
| 工具与确认 | 四类工具、确认、版本和防重复 | 正常、缺项、风险、冲突、失败及副作用测试 |
| 模型与 CLI | 真实工具循环、Mock、demo/review | 协议、预算、CLI 集成和真实模型最小路径 |
| 评估与交付 | 实际证据、修复、运行说明、最终材料 | 全部验收映射、干净安装、实际模型结果和限制 |

阶段完成后先检查变更，再验证、暂存明确范围、核对暂存内容并提交；用户正在修改的无关文件不得顺带提交。发现问题则修复并重跑相关检查，不能通过跳过钩子完成正常交付。
本地提交不自动意味着创建 GitHub 仓库或推送；远程发布依照用户明确要求执行。

## 消息格式

采用 Conventional Commits 风格，标题格式：`type(scope): 具体结果`。标题不超过 72 个字符，scope 使用小写英文。描述可中文，直接说明结果。

允许类型：feat、fix、docs、test、refactor、perf、build、ci、chore、revert。破坏性变更用 `!` 并在正文说明；不主动制造破坏性变更。

示例：

```text
feat(storage): 实现草稿事务保存与重复请求复用

增加 request_id 与 material_id 唯一约束，明确保存失败状态。

验证：存储事务、跨进程重复请求和冲突测试通过。
限制：真实模型尚未接入。
```

正文记录必要原因、实际验证和限制；仅文档变更要注明未进行业务测试。不得写密钥、Token、真实隐私或虚构测试成绩。
常规改动不 amend 已完成阶段，不 rebase、force push 或改写历史；纠错用新的 fix/docs 提交。多行消息通过文件或结构化参数传入，不拼接不安全的 shell 内容。

## 本地自动检查

仓库使用 `.githooks`，初始化后设置：`git config core.hooksPath .githooks`。

- pre-commit 调用 scripts/check_staged.py：拒绝暂存 .env、运行数据库、凭据类文件及常见 Token 格式；与本地 .env 内密钥值做精确匹配，报错只含路径和原因。
- commit-msg 调用 scripts/check_commit_message.py：检查标题格式与长度。
- .gitattributes 统一文本 LF，保证 Git hook 在 Windows Git shell 中可运行。

钩子使用本机 python，未安装解释器时先按 README 配置。它们是本地辅助检查，不是完整的密钥检测系统，无法保证识别所有凭据；提交前仍核对暂存范围。
克隆者需要显式设置 core.hooksPath；Git 不会仅因克隆仓库就自动安装钩子。

## 凭据与文件

真实凭据保存在已忽略的本地 .env；.env.example 只含空值或公开配置。DEEPSEEK_API_KEY 只用于必要模型调用；GITHUB_FGT 仅在用户要求的 GitHub 操作中使用。
Token 不放在 remote URL、命令行参数、提交消息或日志，不执行会显示 .env 内容的命令。API 状态只报告是否配置，不报告值。
runtime/、虚拟环境、缓存和本地数据库不提交；经核查的合成证据放 examples/。最终提交的 SHA 由 Git 实际返回，不预填；若后续增加材料，最终 SHA 随最后交付提交更新。

## 提交后

检查 git status 和实际提交摘要；向用户简要报告改动、验证、限制与短 SHA。记录真实阶段完成情况，不声称本地 commit 已推送 GitHub。
