# 同类产品与用户使用方案

状态：2026-10-30 产品使用设计，尚未实现或开展用户测试。本文补充架构基线的 CLI 使用体验，不引入 Web 服务或真实发布。具体产品功能以引用的官方文档为准，不对国内平台接入或套餐覆盖作推断。

## 1. 同类工具

| 工具 | 官方资料展示的操作 | 对本项目的启示 |
| --- | --- | --- |
| Planable | 工作区内创建内容、在日历查看帖子、发起单条或批量审批请求；支持不同审批工作流 | 围绕同一内容条目组织建议、修改和确认，不能只展示脱离内容的聊天 |
| Buffer | 创建草稿、请求审批、查看待审批列表；日历可按渠道和状态筛选 | 草稿需要能找回；审核状态与排期位置应同时可见 |
| Sprout Social | 创建带媒体和元数据的帖子、选择审批流程、审批或退回；原定时间前未获批时需重设时间 | 截止时间和未决审批要明确，审批不等于实际发布成功 |

来源：[Planable 请求审批](https://help.planable.io/hc/en-us/articles/21715207498652-Requesting-approval)、[Planable 入门](https://help.planable.io/hc/en-us/articles/21715323068444-Getting-started-with-Planable)、[Buffer 草稿审批](https://support.buffer.com/en-us/articles/managing-and-approving-draft-posts-57li7M8tDA)、[Buffer 日历](https://support.buffer.com/en-us/articles/how-to-use-buffers-calendar-feature-FSSKbH32DN)、[Sprout Social 审批](https://support.sproutsocial.com/hc/en-us/articles/205974715-Message-Approval-Workflows)。

它们是内容协作、审批与发布管理产品。官方文档能证明上述功能，不据此推断它们一定采用或没有采用本题要求的模型决策循环。
本项目聚焦规则和冲突出现后的主动处理及可验证草稿；不是对完整商业系统的功能复刻。真实业务中可考虑作为现有工作台的助手或插件，这只是演进方向。

## 2. 用户与呈现

考核版第一用户是能够运行本地项目的评审或候选人；业务体验参照运营人员。项目最终包含可安装 CLI、可选择的合成场景、中文终端摘要、持久化草稿、可重复运行的证据和测试。
业务层展示素材标题、平台账号、原要求、风险、替代方案及具体待办。模型名称、内部枚举、工具 JSON 和调用记录放在详细证据，不要求用户阅读它们才能做决定。

提供两类入口：

- 交互入口：demo 一键演示，review 选择待办并逐项确认；不要求手写确认 JSON。
- 自动化入口：seed / run / confirm / inspect-draft 保留，方便测试、真实模型评估与复现。

首版演示场景预置三条素材；实际六个验收场景分开保存证据。演示不能代替全部验收，更不能用 Mock 的结果证明真实模型能力。

## 3. 使用旅程

1. 安装：按 README 创建虚拟环境、安装锁定依赖。demo 默认 Mock，无需密钥；live 需配置 API 密钥并显式选择，界面明确标记模式。
2. 试用：demo 加载隔离的合成数据并执行模型工具循环，显示正在检查的素材和可理解的进度。重复演示不覆盖用户数据库；重置测试数据库必须显式指定。
3. 查看：展示处理总数、无待确认项、待补资料、待确认、阻断、保存失败或未知等摘要；有重叠的维度需分列而不能把计数相加当作总数。
4. 处理：review 从当前数据库列出待办，展示某条素材的风险与证据、原时间、候选时间、草稿版本。用户选择接受替代、拒绝或暂不处理；不能接受硬性阻断为通过。
5. 确认：程序先复核当前版本、规则和占用，再展示确认的精确方案。用户显式确认后写入当前草稿；若复核导致方案变化，不沿用先前确认。
6. 缺资料：给出缺少的具体字段与输入位置；首版由用户修改合成数据文件并显式重新导入，再重评估。真实业务直接编辑资料的界面留待后续实现。
7. 错误：明确失败环节、保留成功部分、展示可恢复动作。重跑使用同一 request_id，避免多建草稿；unknown 时先核对存储。
8. 交接：导出或生成最新 summary.md 和 output.json；展示 draft_id、revision、生成时间和未决事项。历史报告注明是快照，当前状态用 inspect-draft / review 读取数据库。

边界说明：补齐素材事实并导入后，原请求可重跑；补齐请求中的空时间字段或改变原要求、候选范围时，应建立独立新请求。新请求不会自动替代旧草稿，旧有效草稿继续参与本地占用。首版不提供原要求就地编辑、自动替换请求或已确认方案撤回；review 的拒绝只适用于当前 active 修订中的未决可确认项，已拒绝方案重跑不会恢复。
无可用时段时，显示原时段及候选的冲突证据，提示修改要求或扩大候选范围，不提供“接受空建议”按钮；已有可用替代建议时，先保存待确认草稿，再供用户决定。缺资料和调整范围属于输入待办，不能通过确认菜单补造事实。同方案复用保留已作出的有效确认，不要求用户重复批准。

## 4. 终端摘要示例（设计，非真实输出）

```text
本次处理 3 条素材；模式：离线 Mock（仅验证流程）

M01 新品介绍视频 · 抖音 / 官方账号
规则预检：通过
原要求：11 月 3 日 18:00 +08:00（硬性）
发现问题：该时段已有安排 S01
建议：同日 19:00，目前在本地规划中可用
需要你决定：是否接受 19:00 的替代建议？
草稿：已保存 D001，第 1 版；尚未确认，未发布

M02 门店花絮
需补充：配乐授权来源。补齐后重新检查。
草稿：未保存（资料不足）

M03 活动预告
审核和时段检查已完成；保存失败：数据库锁定。
请稍后使用相同请求重试。
```

review 使用数字菜单列出具体选项，显示精确日期、时区、账号与版本；“接受替代时间”与“接受可人工裁量风险”分别确认。退出或默认选择均为暂不处理，不自动确认。
用户拒绝任一未决可确认项，即拒绝整份方案并释放本地容量；无待确认项或已全部确认的草稿不能通过该菜单撤回。业务必填项按明确规则展示，不能因示例包含某字段就要求补齐。

### 默认候选与指定时间的取舍

Buffer 区分默认队列时段与用户指定精确时间，后者不必遵循默认排期；预设草稿时间也不会自动发布。Planable 可配置审批后锁定内容，修改前须先撤销批准。这些是可核查的产品行为，不据此推断其数据库实现。[Buffer 排期机制](https://support.buffer.com/en-us/articles/setting-up-your-timezones-and-posting-schedules-P4iSag90Fl)、[Buffer 草稿](https://support.buffer.com/articles/saving-and-scheduling-draft-posts-CBLXg1yFXp)、[Planable 审批](https://planable.io/guides/content-approvals-in-planable/)。

本项目据此将 allowed_slots 仅作为默认候选；用户显式时间无需与其取交集，可明确跨日；省略/null 使用请求时区同日默认候选，[] 表示没有替代空间。任何时间仍需核查占用，任何改期仍需确认；通过修订失效旧确认防止“批准后方案悄悄变化”。不引入这些产品的真实发布、自动队列跨日填充或企业权限功能。

## 5. 不方便及应对

| 不方便 | 首版解决 | 后续真实产品方向 |
| --- | --- | --- |
| 安装和配置复杂 | 精确环境、锁定依赖、一键 Mock 演示、明确缺配置错误 | 桌面打包或托管运行 |
| 手写请求和确认 JSON 容易出错 | 示例请求、demo 和 review 数字菜单；JSON 保留给测试 | 表单或接入现有内容工作台 |
| 不知道为何建议某时段 | 显示原要求、冲突来源、候选范围与简短建议理由 | 可视日历与内容预览 |
| 审核通过、确认和保存容易混淆 | 中文分列展示，明确“通过规则预检”“待确认”“草稿已保存” | 同一内容卡片内操作 |
| 等待模型时不清楚是否卡住 | 阶段进度、耗时、明确超时、保留部分结果 | 可恢复后台任务 |
| 报错后重跑担心重复 | 相同请求复用或修订同一草稿，展示实际保存结果 | 一键重试和操作历史 |
| 确认后内容或占用变化 | 版本复核、过期确认拒绝、展示变化后再确认 | 实时更新提示 |
| 素材资料和排期需要重复录入 | 首版合成数据统一维护、显式导入；承认仍有人工维护成本 | 导入表格或连接已有资料库与日历 |
| 多人协作和权限不足 | 文档明确本地单操作者边界，不伪造审批身份 | 账号权限、审核分工与通知 |

## 6. 功能优先级与 CLI 设计增补

保留架构基线的四类模型工具及所有必验项。新增的是展示与交互入口，不增加 Agent 工具，不改变存储或确认规则。

首版应提供：demo、中文摘要、review 交互确认、失败恢复说明和明确模式提示。demo/review 复用 run/confirm 服务逻辑，不另造一套审核或保存流程。

拟定入口（尚未实现）：

```text
python -m shadow_agent demo
python -m shadow_agent review --db runtime/agent.db
```

CSV 导入、HTML/日历界面、内容媒体预览、提醒通知及现有工具连接暂为后续迭代，不挤占三小时核心链路和真实模型证据的验证时间。
