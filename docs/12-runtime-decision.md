# 运行方式与 Agent 实现取舍

状态：设计决策，未实现。用户已明确选择 CLI。

## 决定

采用 Python 3.13 + argparse CLI + 原生单 Agent 工具循环。
真实模型通过 HTTPX 调用 DeepSeek Tool Calls，Pydantic 校验契约，SQLite 存储业务状态，pytest 验证行为，Ruff 检查代码。
不引入 Agent Runtime 框架，也不自行开发通用 Runtime。

CLI 同时提供可复制命令和终端交互。demo 用预置数据，review 用菜单确认具体草稿；run / confirm 保留结构化输入，满足测试与自动化需要。所有入口共用业务服务。

## 原生实现适合当前范围的原因

当前只有单 Agent、四类工具和短时任务。核心复杂度在审核、冲突、确认和草稿去重，而不是多 Agent 编排。
采用原生实现，模型动作、工具参数、结果回传、终止与预算在同一个小型循环中可直接审查；受控模型替身也便于注入不同观察和错误。
三小时预算优先用于业务规则、真实模型证据与验收；不以框架名称衡量完成度。

## 成本与明确边界

原生方案必须自己正确处理工具调用 ID、消息历史、参数校验、错误观察、预算、超时、结果校验和 Trace；这些不能省略。
SQLite 保存的是业务草稿、修订和确认，不是模型执行栈的完整检查点。进程退出后从已保存业务状态重新评估，不承诺从任意模型步骤精确续跑。
不实现分布式执行、通用工作流引擎、长期对话记忆、通用插件系统或后台等待审批。
人工确认时结束当前任务并返回 needs_input，后续由独立 CLI 操作读取并复核草稿，避免让模型进程一直等待。

## 备选框架

- LangGraph：官方描述了图式状态编排及检查点等能力。若未来必须支持跨进程精确恢复模型流程、长时间等待人工后继续执行、多条并行分支与汇合，应重新评估引入。
- AgentScope：官方提供现成 ReActAgent。若要复用其 Agent、工具和消息抽象，可做最小适配试验，比较代码和验证成本。
- Google ADK：官方提供不同 Agent 与工作流组织方式。若项目后续确实需要该生态的运行或集成能力，再评估其收益。

以上是适配当前需求的判断，不是三个框架的性能排名，也不是已进行过的同条件实验。
来源：[LangGraph 参考](https://reference.langchain.com/python/langgraph/overview)、[AgentScope ReActAgent](https://doc.agentscope.io/tutorial/quickstart_agent.html)、[Google ADK 工作流](https://github.com/google/adk-docs/blob/main/docs/agents/workflow-agents/index.md)。

## 原生循环仍必须由模型驱动

模型选动作 → 参数与权限校验 → 工具实际执行 → 观察回传模型 → 模型重新选择动作或结束。
不能用固定分支代替模型决策；程序规则负责确定性边界。至少两条真实模型 Trace 证明工具观察变化影响后续动作。

## 模型选择与待验证项

DeepSeek API 是当前默认接入方案，依据是其官方工具调用协议适配本任务。默认模型名沿用架构基线，非 thinking 模式简化对话消息处理，不收集内部思维过程。
这不是基于实际质量、延迟或费用的优胜结论；网页聊天可用也不能证明 API 凭据或额度可用。
实现时先做工具调用与观察回传的最小真实测试，再运行正常、冲突和异常场景，记录模型配置、有效工具调用、任务结果和预算。

## 如何证明取舍与修改有效

1. 按六个必验场景运行并保存真实输出，分别报告 Mock 流程与真实模型结果。
2. 更换占用时段，观察模型是否改查候选或请求确认；重复提交核查数据库唯一草稿。
3. 修复或修改前记录具体失败，修改后重跑同一用例并记录影响；不能预先编造改进结果。
4. 只有出现明确的编排或恢复需求时，才进行框架适配实验，并比较代码职责、失败恢复和同一验收集结果。
